# dashi-taskboard 安装到 Codex 的最佳实践

这份记录总结了在 Windows 版 Codex 中安装、启动并注入 dashi-taskboard 面板时遇到的问题和稳定做法。

## 推荐启动方式

优先使用仓库根目录下的启动脚本：

```bat
D:\Sources\Github\dashi-taskboard\start-codex-taskboard.bat
```

启动后保持控制台窗口打开，或者最小化。这个窗口里的注入进程会驻留运行，用来维持 Codex 侧边栏里的任务面板，以及在本地任务面板服务断开时恢复服务。

## 基本流程

1. 关闭正在运行的 Codex。
2. 双击 `start-codex-taskboard.bat`。
3. 如果提示需要重启 Codex，选择 `Y`。
4. 等待脚本完成以下阶段：
   - 关闭旧的 Codex 进程
   - 启动带调试端口的 Codex
   - 等待 Codex 主窗口出现
   - 启动或恢复本地 Taskboard 服务
   - 注入任务面板 tab
5. 在 Codex 左侧点击“任务面板”。

## 控制台窗口能不能关闭

当前脚本使用 `npm run codex:inject -- --watch`。这意味着控制台窗口不是单纯的启动器，而是一个驻留守护进程。

不要在使用任务面板时关闭控制台窗口。关闭后，已经注入的面板可能暂时还在，但 Codex 刷新、窗口重建、服务断开或重新打开后，任务面板可能消失或卡在启动中。

建议：

- 使用时保留控制台窗口。
- 不想看到它时最小化。
- 不用任务面板后，再关闭控制台和 Codex。

## 已确认的关键问题和解决方案

### 1. Codex 不支持直接 iframe 本地页面

现象：

- 左侧能看到“任务面板”tab。
- 点击后右侧一直显示“正在启动任务面板”。
- 调试日志中出现 Content Security Policy 的 `frame-src` 拦截。

原因：

Codex 的页面安全策略不允许直接把 `http://127.0.0.1:47823` 放进 iframe。

解决：

注入脚本需要用 `blob:app://-...` 作为 iframe 地址，再在 blob 页面里加载本地 Taskboard 的 HTML、JS、CSS。

### 2. blob 页面里的资源路径必须改成绝对地址

现象：

- iframe 已变成 `blob:app://-...`。
- 但页面仍然卡在“正在启动任务面板”。
- 控制台出现 `Unexpected token '<'`。

原因：

Taskboard 的 HTML 里使用 `/assets/...` 这种根路径。进入 Codex 的 `app://-` 环境后，浏览器会尝试加载 `app://-/assets/...`，拿到错误内容后当 JS 执行，于是报错。

解决：

在 blob 引导页中解析 Taskboard HTML，并把 `/assets/...` 这类路径改成：

```text
http://127.0.0.1:47823/assets/...
```

### 3. 本地服务需要允许 Codex 的 app origin 访问

现象：

- blob 页面可以加载。
- 但 JS、CSS、API 或 EventSource 请求被 CORS 拦截。

原因：

嵌入后的页面 origin 是 Codex 的 `app://-`，访问本地服务时属于跨域请求。

解决：

本地 Taskboard 服务需要给可信的 Codex origin 返回 CORS 头，并允许常用 API 请求头。

### 4. 等待 Codex 调试端口不要用 PowerShell 网络请求

现象：

- BAT 卡在 `Waiting for Codex debug port...`。
- 实际上 Codex 进程已经带着 `--remote-debugging-port=9231` 启动。
- `curl http://localhost:9231/json/version` 能返回，但 PowerShell `Invoke-RestMethod` 偶发超时。

解决：

BAT 中检测 Codex 调试端口时使用 `curl.exe`，检测主窗口列表时使用 Node `fetch`，避免 PowerShell 网络请求卡住。

### 5. 重复启动前要清理 Codex 后台进程

现象：

- 第一次运行 BAT 成功。
- 关闭 Codex 后再次运行，偶尔卡在等待调试端口。

原因：

Windows 版 Codex 关闭窗口后，可能仍残留 `ChatGPT.exe` 或 `codex.exe` 后台进程，导致 9231 端口处于不稳定状态。

解决：

启动脚本在重新启动 Codex 前应清理：

- `ChatGPT.exe`
- `codex.exe`
- 9231 上的旧监听状态

并等待端口释放后再启动 Codex。

### 6. 注入目标要避开辅助窗口

现象：

- 注入日志异常关闭。
- 或注入到了 Codex 的辅助窗口，不是主窗口。

原因：

Codex 会创建一些辅助页面，例如 avatar overlay 或 dictation overlay，它们也可能出现在 CDP target 列表中。

解决：

注入器只选择主窗口：

```text
type = page
url = app://-/index.html
```

并排除：

```text
initialRoute=%2Fglobal-dictation
initialRoute=%2Favatar-overlay
```

## 稳定性检查命令

检查本地 Taskboard 服务：

```bat
curl.exe http://127.0.0.1:47823/health
```

检查 Codex 调试端口：

```bat
curl.exe http://localhost:9231/json/version
```

检查 Codex 主窗口是否可被注入器发现：

```bat
node -e "fetch('http://localhost:9231/json/list').then(r=>r.json()).then(ts=>console.log(ts.some(t=>t.type==='page'&&t.url==='app://-/index.html')?'main-ok':'main-missing'))"
```

手动重新注入：

```bat
cd /d D:\Sources\Github\dashi-taskboard
node scripts\codex-injector.mjs --port 9231 --open --attach-existing
```

## 排障顺序

遇到问题时，建议按这个顺序查：

1. 确认 BAT 控制台还开着。
2. 检查 `curl.exe http://127.0.0.1:47823/health` 是否正常。
3. 检查 `curl.exe http://localhost:9231/json/version` 是否正常。
4. 检查 `http://localhost:9231/json/list` 中是否有 `app://-/index.html`。
5. 手动执行注入命令看输出。
6. 如果 tab 有了但页面卡住，重点看 iframe、CSP、CORS 和资源路径。

## 最终建议

最稳的 Windows 使用方式是：

- 使用一个固定端口启动 Codex 调试服务，例如 `9231`。
- 本地 Taskboard 服务固定使用 `47823`。
- 注入脚本保持 `--watch` 常驻。
- 控制台最小化，不要关闭。
- 所有网络探测优先用 `curl.exe` 或 Node，不用 PowerShell 的 `Invoke-RestMethod` 做循环等待。
